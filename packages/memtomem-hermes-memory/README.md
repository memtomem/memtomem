# memtomem-memory for Hermes Agent

A recall-only Hermes memory provider. On each user turn it looks up your memtomem long-term
memory and gives Hermes the most relevant notes as context for that turn, without the model
having to call a tool. It uses the memtomem MCP server you already run in Hermes; it starts
no server of its own.

`plugin.yaml` is generated by `tools/render_plugin_assets.py` from
`packages/memtomem-plugin-assets/contract.toml`; `__init__.py` and this README are
hand-written.

## What it does and does not do

- It recalls. On every non-trivial user turn (not greetings, acknowledgements or slash
  commands) it searches memtomem for the turn's message and injects the results under a
  one-line heading, "Recalled from memtomem". By default that is up to five results in at
  most 4,000 characters of bullets, not counting the heading (see [Settings](#settings)).
- It does not write. It adds no tools for the model, does not save conversations, extracts
  nothing, mirrors nothing and adds no line to the system prompt. Saving notes is what the
  memtomem MCP tools are for.
- It waits for the search at most 300 ms by default (`budget_ms`). A search that takes
  longer is not used for that turn.

## Requirements

- Hermes Agent 0.21.5 or later, with MCP support (the `hermes-agent[mcp]` extra).
- A Hermes MCP entry named `memtomem` that runs memtomem 0.6.8 or later: either the memtomem
  plugin from `packages/memtomem-hermes-plugin`, or your own `mcp_servers.memtomem` entry in
  `config.yaml`. Earlier memtomem releases do not confirm that a search records nothing, and
  this provider refuses to use them.
- Git on `PATH`, for the commit lookup under [Install](#install).

## Install

Install from this repository, pinned to the commit of a memtomem release tag. Hermes
(0.21.5) takes a full 40-character commit SHA for `--ref` and refuses a tag name such as
`v<version>`, so look the commit up first:

```bash
git ls-remote --exit-code https://github.com/memtomem/memtomem "refs/tags/v<version>" "refs/tags/v<version>^{}"
```

The command prints one line for a lightweight tag and two for an annotated one; no output
and exit status 2 mean there is no such tag. Copy the SHA at the start of the line that ends
in `^{}` if there is one, otherwise of the only line, and install at it:

```bash
hermes plugins install "https://github.com/memtomem/memtomem#packages/memtomem-hermes-memory" --ref <commit-sha>
```

Then select the provider and grant it access to the `memtomem` MCP entry in
`~/.hermes/config.yaml` (or your profile's `config.yaml`):

```yaml
memory:
  provider: memtomem-memory
plugins:
  entries:
    memtomem-memory:
      mcp_allowlist: [memtomem]
```

Start a new session. Without the `mcp_allowlist` grant Hermes lets no plugin call an MCP
server, and the provider reports itself unavailable with the line to add.

## What it calls and when

On every non-trivial user turn, without a model tool call, it makes one `mem_search` call
on the MCP entry named `memtomem` through Hermes's own MCP client, with `record=False`
(nothing is written to memtomem's access counts or query history) and `rerank=False`.

It owns no server. If the `memtomem` entry has not started yet, the first recall makes Hermes
start it, and that first turn gets no recall while memtomem loads its models (a few seconds).

What that call reaches is whatever the entry's memtomem configuration reaches: its store,
the `.env` memtomem loads, and the network paths that configuration enables. The memtomem
plugin's README lists those under "Network"
([packages/memtomem-hermes-plugin/README.md](../memtomem-hermes-plugin/README.md#network));
read it at the same release commit you installed.

## Which entry it uses

- A `mcp_servers.memtomem` entry in `config.yaml` wins over the memtomem plugin's entry of
  the same name, even when it is disabled and even when it pins an older memtomem.
- One exception: Hermes drops a native entry that its MCP security check flags and uses the
  plugin's entry instead. The provider does not repeat that check. It still reads the
  dropped native entry's `enabled` and `trust`, so it can refuse recall that Hermes would
  have served through the plugin's entry.
- The provider checks every answer. A server that does not confirm `"recorded": false` is
  older than memtomem 0.6.8; recall stays off, with one warning in the log, until the entry
  runs a newer release.
- A disabled entry, a missing entry or a missing `mcp_allowlist` grant turns recall off on
  the next turn, with one warning, and nothing is called.

## Sharing the connection with the model

Recall uses the same connection, call queue and circuit breaker as the model's own memtomem
tools. To keep recall from crowding those out, the provider:

- makes at most one recall call at a time per MCP entry name, across every session and
  profile in the Hermes process. A turn that starts while another session's recall call is
  still running gets no recall;
- waits 15 s after a failed call before trying again, then 60 s, then 300 s for every further
  consecutive failure. A successful call resets the schedule.

Hermes opens an entry's circuit breaker after three consecutive failed calls and then refuses
the model's calls to it too. At the default settings (a 10 s call timeout and the 15/60/300 s
waits above) recall alone reaches three failures only after about the times below. They are
estimates for these scenarios, and they shrink with a shorter `rpc_timeout_seconds` or
shorter waits:

- about 105 s of continuous failure, for a server that stalls or a call queue held by one
  long model operation;
- about 75 s, for an entry whose server is not running;
- about 60 s for a stalling server, or about 30 s for one that is not running, when another
  profile's healthy server runs under the same entry name: its successful recall resets the
  schedule between failures. During each of those waits the healthy profile's recall pauses
  too.

The next successful call on the connection closes the breaker again: a long model operation
such as a large `mem_index` finishing, a model call, or recall's own next attempt. When the
server stalls, recall is empty and the model may see Hermes's breaker message.

The first call after the server starts holds the entry's one recall slot while memtomem loads
its models, so every session's recall on that entry pauses for up to a few seconds.

## Trust

Recall is refused while the `memtomem` entry is not `trust: full`: on an untrusted entry
Hermes would ask for approval on every turn. Hermes applies a changed `trust` value only after
`/reload-mcp`. Until then the provider and Hermes can disagree, and recall may ask for
approval on each attempt. Run `/reload-mcp` after changing `trust`.

## Profiles

The store a profile's recall reads is the one that profile's `memtomem` entry selects,
through the entry's environment. Profiles whose `memtomem` entries are identical share one
connection and one store. For a separate store per profile, give each profile's entry its
own `env` (`HOME` or the `MEMTOMEM_*` paths).

On a shared connection, one profile's `/reload-mcp` interrupts the other's pending recall
call. That call holds the recall slot for up to 15 s (Hermes's wait for the restarted server)
and then starts the first wait, so at the default settings recall on that entry resumes about
30 s after the reload.

Recall runs one call at a time per entry name in the whole process, even for profiles with
separate servers under the same name. While one profile's server stalls, every profile's
recall on that name pauses for the stall plus one wait. That is the price of never adding
more than one failure per wait to a breaker.

## How the model reaches memtomem

By default Hermes offers MCP tools to the model through its tool-search bridge
(`tool_search` / `tool_call`), not as `mcp__memtomem__*` tools. Recall does not depend on
that: it calls memtomem directly, even when a toolset filter hides memtomem's tools from the
model. It does not work when Hermes did not connect the entry at all, for example under a
`--toolsets` selection that leaves it out.

## Settings

Optional, under `memory.memtomem-memory` in `config.yaml`. They are read when a session's
provider starts; a changed value applies to sessions started afterwards. An out-of-range
value falls back to its default with one warning.

| Key | Default | Range |
|---|---|---|
| `server` | `memtomem` | the MCP entry name to call |
| `budget_ms` | `300` | 50–5000 |
| `top_k` | `5` | 1–20 |
| `max_chars` | `4000` | 500–9000 |
| `rpc_timeout_seconds` | `10` | 1–600 |
| `cooldown_seconds` | `15` | 1–300 |
| `long_cooldown_seconds` | `60` | `cooldown_seconds`–600 |
| `max_cooldown_seconds` | `300` | `long_cooldown_seconds`–600 |

A profile whose memtomem entry has another name needs `server` set to that name, and the
same name in `mcp_allowlist`.

## Logging

The provider logs at DEBUG through Hermes's logging, under the logger `memtomem_memory`, one
JSON object per event: `initialize`, `prefetch` (outcome and hook time), `rpc_done` (chunk
ids and sources), `rpc_error`, `rpc_unparsed`, `rpc_incompatible`, `preflight`,
`on_session_switch` and `shutdown`. No log line at any level contains the text of your
message. Warnings name the configuration key to change.

## Compatibility notes

- Hermes 0.21.5 hands a memory provider a registration context without MCP access, so the
  provider builds Hermes's documented `PluginContext` itself to call `call_mcp`. That
  constructor is not part of Hermes's plugin compatibility contract; `call_mcp` is.
- Hermes supports Python 3.11 to 3.13; the provider uses the standard library only and is
  tested on 3.11.
