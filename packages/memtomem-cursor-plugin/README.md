# memtomem for Cursor

> **Experimental**: this plugin is new, so its layout and skills can change without a
> deprecation window. See [Stability](https://github.com/memtomem/memtomem#stability).

Markdown-first long-term memory shared across your coding agents. This plugin starts a
local memtomem MCP server in Cursor and adds the memory workflow skills, including the
session loop: `/memtomem-handoff` saves a checkpoint when a session ends and loads it back
with `resume`, `/memtomem-brief` compiles the project context and the open handoff IDs
when the next session starts, and `/memtomem-update` turns finished work and recent
commits into durable memories (see
[Project workflows](../../docs/guides/project-workflows.md)). Notes saved here are
searchable from Claude Code, Codex CLI, Antigravity and any other client that uses the
same `~/.memtomem` store.

`.cursor-plugin/plugin.json`, `mcp.json` and `skills/` are generated by
`tools/render_plugin_assets.py` from `packages/memtomem-plugin-assets/`; edit the sources
there, not the files here.

## Requirements

- Cursor 3.27.22 or later, the version this plugin was verified against.
- `uv` on the `PATH` Cursor starts MCP servers with. The server is started with
  `uvx --python 3.12 --from 'memtomem[onnx]==0.7.8' memtomem-server`.
- Python 3.12. uv uses a 3.12 it can find; if there is none, it downloads one (about
  70 MiB) on first start. If that is not possible (offline, or uv's Python downloads
  turned off), the server does not start; run `uv python install 3.12` once to fix it.

## Install

Until the plugin is listed in the Cursor Marketplace, install it as a local plugin.
Cursor loads a symlinked local plugin only when the link resolves inside
`~/.cursor/plugins/local`, so copy the directory:

```bash
git clone https://github.com/memtomem/memtomem.git
mkdir -p ~/.cursor/plugins/local
cp -R memtomem/packages/memtomem-cursor-plugin ~/.cursor/plugins/local/memtomem
```

Then run **Developer: Reload Window** and check under **Customize** that the memtomem MCP
server and its nine skills are listed. On a Cursor Enterprise team, an admin has to allow
local plugin imports first. `main` normally pins a published memtomem release, but right
after a version bump is merged it can pin one that is not on
[PyPI](https://pypi.org/project/memtomem/#history) yet, and the server then fails to
start until it is.

To update, pull the clone, delete the installed copy, and copy the directory again.
Copying onto an existing `~/.cursor/plugins/local/memtomem` would nest the new bundle
inside the old one and leave the old one active:

```bash
git -C memtomem pull
rm -rf ~/.cursor/plugins/local/memtomem
cp -R memtomem/packages/memtomem-cursor-plugin ~/.cursor/plugins/local/memtomem
```

Then reload the window. To remove the plugin, delete `~/.cursor/plugins/local/memtomem`;
your memories stay in `~/.memtomem`.

**If you already registered memtomem by hand** in `~/.cursor/mcp.json` or a project's
`.cursor/mcp.json` (see the [Cursor guide](../../docs/guides/integrations/cursor.md)),
the plugin adds a second memtomem server instead of replacing yours. Remove the
hand-written `memtomem` entry to keep a single server.

## First run

No separate setup is needed: on a machine where memtomem has never been configured, the
server uses its defaults (SQLite store in `~/.memtomem/memtomem.db`, notes in
`~/.memtomem/memories`, BM25 search). If memtomem is already set up for your other agents
through `~/.memtomem/config.json`, the server reads that configuration and shares the
same store, provided the storage and memory paths in it are absolute or start with `~`.
A relative path resolves against this server's working directory (your home directory),
so it would open a different store. Ask the agent for memtomem status and check the
reported DB path before relying on sharing.

## Scope

memtomem takes its project context from the directory its server starts in, and Cursor
does not start the plugin's server in the workspace you have open: on macOS with Cursor
3.27.22 it started in the home directory every time, with a repository open or not. So
the server begins at **user scope**. The skills are the ones the Antigravity plugin ships.

Six skills first bind the server to the repository you are working in (`mem_project_bind`,
through `mem_do`), then use its `project_local` tier:

- `/memtomem-search` and `/memtomem-recall` read your user-scope memory plus this
  repository's project memory;
- `/memtomem-remember` saves a project fact to this repository's `project_local` tier and a
  cross-project preference to user scope;
- `/memtomem-handoff`, `/memtomem-brief` and `/memtomem-update` need the repository's
  registered tier and stop without one.

Binding needs:

- a registered tier in that repository: `cd <repo> && mm mem init --scope project_local`;
- a server that is not yet bound to another repository. A binding lasts until the memtomem
  server process restarts, so working in a second repository needs that restart first.

Without a registered tier, or outside a Git repository, search and recall say so and read
user-scope memory only; remember saves only cross-project preferences and personal notes,
and refuses a project fact or a project-only destination rather than storing it in user
scope. The three project workflows stop in both cases, and print the `mm mem init` command
when the repository has no registered tier.

`/memtomem-index`, `/memtomem-status` and `/memtomem-setup` do not bind: paths given to
indexing must be absolute. They read whatever the server has, so after another skill has
bound it, setup's verification search sees that repository's project tier too.

The binding step runs `git rev-parse --show-toplevel` in Cursor's terminal. A Cursor hook
that blocks shell commands, including a Claude Code hook Cursor imports, stops the skill
before it binds.

Remember, index, setup and the three project workflows carry
`disable-model-invocation: true`: Cursor runs them only when you invoke them with
`/skill-name`, never on its own. Search, recall and status may be picked by the agent.

## Network

Memory is stored locally in `~/.memtomem`. The server is downloaded from PyPI on first
start, and uv downloads Python 3.12 then too if it cannot find one. With a fresh
BM25-only configuration nothing else leaves the machine. An existing memtomem
configuration may enable its own network paths: model downloads from Hugging Face (ONNX
embedding or local reranker), a remote embedding or LLM provider, Cohere reranking
(sends the query and candidate chunks), or search webhooks (send events including the
query).
