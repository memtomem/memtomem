# CPU 임베딩 변경 및 측정 결과 — 2026-09-08

신규 ONNX 설정의 기본 모델을 **multilingual-e5-small FP32**로 구현했다.
기존 BGE-M3 설정과 운영 DB는 변경하지 않았다. E5는 CPU 비용이 크게 낮지만,
두 정답 평가에서 BGE-M3보다 검색 품질이 낮았다. **운영 전환은 품질 수용 여부를
검토한 뒤 결정한다.**

## 측정 조건

- 이 Mac: ARM64, 물리 코어 16개, RAM 64 GiB, macOS 26.6.2.
- 추론: Python 3.12.11, ORT 1.24.4, FastEmbed 0.8.0, NumPy 2.4.4,
  Tokenizers 0.22.2. CPUExecutionProvider만 사용.
- 양자화 내보내기: ONNX 1.19.1 / ORT 1.23.2 / NumPy 2.5.3.
- 기본 비교: 스레드 2, 배치 4, CPU arena 비활성화. 모델 다운로드·변환은
  측정에서 제외하고 모델 로딩과 인덱싱을 구분했다.
- 1·2·4스레드 × 1·4·8배치 × 세 모델 옵션 × 독립 프로세스 3회 = **81회**.
  모델 순서는 번갈아 실행했다. RSS는 프로세스 상주 메모리이며 파일 크기나
  전용 물리 메모리와 같지 않다. 데스크톱의 다른 작업에 따른 변동은 남는다.

## 같은 입력으로 비교한 비용과 품질

저장소의 고정 한·영 문서 192개와 정답 질의 120개를 사용했다. 입력은 두 모델
모두 512토큰 안에 들어간다. 아래 시간·RSS는 3회 중앙값이다. Dense 검색만
비교했으며 운영의 BM25·재정렬·LLM 전체 지연으로 해석하지 않는다.

| 모델 | 인덱싱 초 | CPU 초¹ | 질의 p95 ms | RSS MiB | 영어 nDCG@10 | 한국어 nDCG@10 |
|---|---:|---:|---:|---:|---:|---:|
| E5-small FP32 | 1.44 | 3.46 | 2.17 | 1378 | 0.3983 | 0.3097 |
| E5-small INT8 ARM64² | 1.94 | 4.42 | 2.03 | 949 | 0.3918 | 0.3077 |
| BGE-M3 FP32 | 9.31 | 21.89 | 14.67 | 2287 | 0.4889 | 0.4488 |

¹ 초기 로딩을 제외한 인덱싱과 질의의 프로세스 CPU 시간.
² MatMul 양자화. 거대한 임베딩 테이블은 FP32로 남는 옵션이다.

근거: [원본 집계](mac-arm64-fixture-results.json),
[81회 스레드·배치 집계](mac-arm64-sweep-results.json).
E5 FP32는 2스레드·배치 4에서 가장 빠른 축에 들었다. 4스레드로 늘리면 E5
CPU 시간이 약 3.47→7.53초, BGE는 약 21.84→59.12초로 늘었으며 더 빨라지지
않았다. 1스레드는 CPU 사용량을 낮추는 선택이고, 배치 1은 메모리 절약에 유리하다.
따라서 기본값 2스레드·배치 4를 유지했다.

## MIRACL 공개 정답 평가

원본 dev 질의·qrels와 대조한 MTEB 후보 코퍼스에서 언어별 200개 질의를 고정했다.
정답 문서는 모두 포함하지만 부정 판정 문서 **영어 167개·한국어 330개가 누락**돼
있다. 추가 distractor는 언어별 1,000개를 MTEB 후보 코퍼스에서 고정했다.
긴 문서를 손실 없이 나눈 조각은 총 6,610개다. 검색 결과는 원본 문서 ID로
합치고 언어별로 검색했다.

**이 점수는 전체 MIRACL 점수가 아니며 축소 후보 집합에서는 낙관적일 수 있다.**
기본 준비 도구는 판정 문서 누락을 거부한다. 이번 대체 실험은
`--positive-qrels-only`로 누락을 명시적으로 기록했다. 공개 품질은 모델당 1회를
기준으로 삼았다. 최초 혼합 코퍼스 평가 뒤 언어별 정렬을 확인할 때는 문서 벡터를
재사용하여 대량 재임베딩을 피했다.

| 모델 | 영어 nDCG@10 | 한국어 nDCG@10 |
|---|---:|---:|
| E5-small FP32 | 0.7987 | 0.7394 |
| E5-small INT8 ARM64 | 0.7998 | 0.7432 |
| BGE-M3 FP32 | 0.8201 | 0.7853 |
| BGE-M3 INT8 ARM64³ | 0.8223 | 0.7825 |

³ MatMul와 Gather를 양자화한 별도 BGE 후보.
[언어별 정답 평가 집계](mac-arm64-miracl-monolingual-results.json)에는 Recall,
MRR, zero-hit 비율과 양자화 벡터·순위 변화도 있다. 작은 점수 차이를 양자화의
품질 향상으로 일반화하지 않는다.

## 실제 자료와 다중 프로세스

운영 DB는 SQLite backup API로 읽기 전용 백업했고 `MEMORY.md`, 코드,
설정 문서를 별도로 복사했다. 설정 문서 1개는 기존 개인정보 검사에서 차단됐다.
검사를 우회하지 않았으므로 아래는 나머지 두 자료의 결과다.

| 모델별 청크 정책 | 생성 청크 | 최초 인덱싱 | CPU 시간 | 동일 자료 재검사 |
|---|---:|---:|---:|---:|
| E5, 본문 384 / 최종 512 | 632 | 19.03초 | 36.34초 | 0.131초 |
| 기존 BGE, 본문 4096 / 모델 8192 | 339 | 170.94초 | 327.21초 | 0.135초 |

두 재검사 모두 재임베딩 0건이다. 최초 인덱싱은 모델별 1회이며, 모델 크기와
청크 정책이 함께 달라진 전체 정책 비교다. [집계](mac-arm64-clone-summary.json).

별도 복제본에 동일 변경 알림 20개씩을 세 독립 watcher 프로세스에 넣었다.
한 프로세스만 462청크를 생성·임베딩했다. 다른 두 프로세스는 잠금 재시도 뒤
**청크 생성 0회·임베딩 0회·모델 로딩 없음**으로 완료 기록을 재사용했다.
같은 자료를 한 프로세스로 재검사한 시간은 0.137초였다.
실제 queue/debounce/flush 경로를 사용했지만 OS 파일 감시 이벤트 자체를
발생시킨 실험은 아니다. [watcher 집계](mac-arm64-watcher-summary.json).

실제 검색 기록 14,221건에는 독립적인 정답 판정이 1건뿐이었다. 과거 검색 순위를
정답으로 삼지 않고 100개 질의를 성능 재생용으로 고정했다. 구성은 한글 전용
40개·영문 스크립트 40개·혼합 스크립트 20개이며, 혼합 스크립트를 교차 언어
정답 사례로 주장하지 않는다. 동일 본문 조각 632개는 모델별 한 번 인코딩하고,
질의는 독립 프로세스에서 세 번 재생했다.

- 질의 p95 중앙값: E5 **7.27ms**, BGE **45.53ms**.
- 100개 질의 CPU 시간 중앙값: E5 **0.84초**, BGE **5.06초**.
- 모델 간 top-10 일치율: **14.5%**. 정답이 없으므로 이를 품질 하락률로
  해석할 수 없다. 실제 사용 질의의 별도 정답 검토가 필요하다.

[개인 자료 집계](mac-arm64-private-replay-summary.json)만 저장소에 포함했다.
원문·질의·DB 복제본은 저장소 밖에 보관한다.

## CPU 장치별 모델 선택

이 Mac에서는 FP32가 두 모델 모두 INT8보다 인덱싱이 빨랐다. INT8을 자동 기본값으로
올리지 않았다. E5 MatMul INT8 파일 묶음은 약 424MB, Gather까지 양자화하면
약 135MB지만, 후자의 RSS는 약 935MiB로 전자의 약 949MiB와 큰 차이가 없었다.
**파일 크기 감소를 RAM 감소나 처리 속도 향상으로 치환하면 안 된다.**
[Gather 후보 결과](mac-arm64-gather-results.json).

- macOS ARM64: 기본 FP32 2스레드·배치 4. CPU 총량 우선이면 1스레드,
  메모리 우선이면 작은 배치와 INT8 후보를 검토한다.
- Windows/Linux x86-64와 Intel Mac: FP32로 시작하고 AVX2/AVX512/VNNI 후보는
  해당 호스트에서 검증한다. 이번 세션 실기기 결과는 **NOT_RUN**이다.
- Windows/Linux ARM64도 **NOT_RUN**이다. ORT 배포판 지원을 먼저 확인한다.
- FP16/O4는 CPU 공통 기본값으로 선정하지 않았다. INT4/OpenVINO는 이번 범위 밖이다.
- stdio MCP 구조는 유지했다. 세션마다 모델을 로드하는 검색·명시적 warmup의
  상주 비용까지 공유하는 구조로 바꾼 것은 아니다.
- ORT thread spinning도 추가 검토 대상이지만 현재 FastEmbed의 공개 세션 옵션은
  CPU arena만 허용한다. 이번 변경에서 비공개 monkeypatch로 설정하지 않았다.

Mac/Ubuntu/Windows 실모델 smoke 워크플로를 추가했다. **워크플로 작성과 실제 CI
통과는 별개이며 원격 실행은 하지 않았다.**

## 원인 판단과 구현 범위

과거 고부하 PID의 로그에는 `MEMORY.md` 약 244개 청크 인덱싱이 남아 있었다.
당시 세대별 내용 해시가 없어 여러 클라이언트가 동일 내용을 중복 임베딩했는지,
파일이 실제로 다시 바뀌었는지는 확정할 수 없다. 모델의 최대 길이가 8192라는
사실만으로 항상 8192토큰을 처리했다고 추정해서도 안 된다.

이번 변경은 더 작은 모델, 최종 입력 예산, 5초 quiet window / 최대 30초 수집,
완료한 파일 세대 재사용, 적은 스레드·배치로 각각 비용을 줄인다. 읽기·잠금·청크·
임베딩·DB 기록 시간을 로그에 구분했다. 최대 30초는 이벤트 수집 상한이며 이미
진행 중인 추론이나 잠금 대기까지 30초 안에 끝난다는 보장은 아니다.

청크 적용 경로·설정·재현 명령은 [README](README.md)와
[설정 안내](../../docs/guides/configuration.md)에 정리했다. E5는 접두사·제목·문맥·
특수 토큰까지 센 512토큰 상한을 사용한다. 양자화 파일과 토크나이저는 검증하고,
기존 namespace·개인정보 검사·source-read-only·원본 span 검증을 유지했다.

최종 로컬 검증(2026-09-09): 전체 테스트 **15,142개 통과 / 372개 건너뜀**,
마지막 변경 관련 테스트 **368개 통과**. mypy는 366개 소스 파일에서 오류가 없고,
Ruff lint, 변경 범위 포맷, JavaScript 구문, extras import coverage,
기준선 대비 Bandit 보안 검사와 `git diff --check`를 통과했다.
저장소 전체 포맷 검사에는 변경하지 않은 `.github/cla-check.py`의 기존 위반 1개가
남아 있으며, 기준 커밋의 같은 파일에서도 재현했다.

운영 설정 적용,
전체 코퍼스 메타데이터 보존 마이그레이션, 공유 세션 재시작, PR/원격 CI/병합은
수행하지 않았다. 복제본은 평가용이며 운영 DB 교체 파일이 아니다.
