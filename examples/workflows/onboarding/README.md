# 프로젝트 이해·온보딩

**처음 맡은 기능의 구조와 결정 이유를 근거와 함께 파악합니다.**
신규 합류자뿐 아니라 기존 구성원이 낯선 기능을 맡을 때도 사용합니다.

## 첫 체험

[공통 설치](../README.md)를 마친 뒤 저장소 루트에서 실행합니다.

```bash
.venv-workflows/bin/python examples/workflows/demo.py --workflow onboarding
```

`billing webhook retry`를 결정 문서·Python 구현·production 설정에서 차례로 찾습니다.
결제의 3회 재시도와 알림의 5회 재시도를 혼동하지 않아야 합니다. 검색 결과를
[작업 준비 양식](template.md)에 옮기고 파일 경로를 확인합니다.

## 내 프로젝트로 옮기기

1. 유지보수자가 README, 설계 결정, 운영 절차, 지원되는 코드·설정 파일을 선택합니다.
2. 신규 구성원이 접근 가능한 자료를 로컬에서 색인하고, 맡은 기능을 질문합니다.
3. 결정·구현·설정·테스트 위치를 확인해 작업 준비 메모를 작성합니다.
4. 설명이 빠진 부분은 질문으로 남깁니다. 확인된 새 설명만 검토 후 기록합니다.

```text
아직 코드를 변경하지 마세요. memtomem에서 [기능 식별어]를 검색하고 원문을 확인하세요.
기능 개요, 현재 정책, 결정 이유, 구현·설정·테스트 위치를 출처와 함께 정리하세요.
이전 정책·제안과 현재 정책을 구분하고 서로 다른 도메인의 설정을 섞지 마세요.
문서와 코드가 충돌하면 차이를 그대로 적으세요. 없는 설명은 미확인 질문으로 남기세요.
첫 작업을 준비하기 위해 무엇을 더 확인해야 하는지 제안하세요.
```

## 성공 확인과 재사용

[evaluation.json](../evaluation.json)의 `onboarding` 10개 과제로 근거 경로를 확인합니다.
관련 파일을 찾은 시간과 설명의 정확성을 별도로 기록합니다. 테스트 파일을 찾았다는 사실은
테스트 실행이나 코드 변경의 안전성을 증명하지 않습니다.

유지보수자가 첫 기여자나 팀 동료에게 자료 묶음을 전달합니다. 다음 주에는 다른 기능이나
변경된 정책에 같은 과정을 적용하고 [사용 일지](../pilot/participant-log.md)를 작성합니다.
추가 탐색에는 [Slateharbor 전체 실습](../../onboarding/slateharbor/README.md)을 활용하세요.
